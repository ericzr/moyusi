# 产品架构与开发主线

状态：Stage 2 已启动
日期：2026-08-28

## 1. 产品目标

Moyusi 只保留两个一级产品面：

1. **模型广场**：围绕语言、图片、视频任务，统一展示闭源 API、开放权重模型及其多种供给来源；用户购买的是访问能力、用量或算力，不是模型所有权。
2. **工作台**：把 CC Switch 类路由切换、平台 Key、BYOK、开放模型端点、用量计费、账户，以及 MCP/Skills/Prompts/记忆/知识库的可迁移工作环境放入同一控制面。

产品的核心价值不是“模型列表更多”，而是让一次选择形成可追踪闭环：

```text
发现模型
  → 比较具体供给
  → 明确统一余额 / BYOK / 共享算力 / 专属算力 / 自有端点
  → 完成授权、预算或接入确认
  → 写入工具路由
  → 发起调用
  → 用量、价格版本与账本可追溯
```

Moyusi 不在首期建设通用聊天产品、复杂社区、模型排行榜或自营全量算力云。这些能力会稀释“选择、接入、切换、计费、迁移”的主闭环。

### 第一性原理与删除测试

- 用户要的是任务结果，不是学习模型协议、端点和路由术语；模型广场先回答“适合做什么”。
- 同一型号不等于同一服务；来源的价格、响应/排队、稳定性、结算方式和数据边界必须可以直接比较。
- “一键”不是省略安全工程，而是把验证、备份、差异检查、原子写入和回滚放在后台完成。
- AI 配置迁移不是复制一个文件，而是统一管理资产、生成目标适配、重新授权敏感权限并报告损失。
- 任一功能若不能帮助用户发现、比较、切换、迁移，或理解费用与风险，就不进入主界面。

因此首期删除：营销 Hero、模型 Logo 墙、综合排行榜、社区评价、无行动意义的仪表盘、协议优先筛选、同时展开全部专业设置，以及与核心闭环无关的通用聊天功能。

## 2. 产品与系统架构

```text
Web：模型广场 + 工作台
  ├── Catalog：模型身份、能力、许可、供给、价格与健康证据
  ├── Access：权限、平台 Key、BYOK 引用、端点与部署订单
  ├── Routing：工具 Profile、路由策略、回退与数据约束
  ├── Billing：用量、定价版本、结算与不可变账本
  └── WorkspaceProfile：MCP、Skills、Prompts、记忆与知识源

Control Plane
  ├── 身份与设备
  ├── Catalog / Offer 管理
  ├── Entitlement / Key 管理
  ├── WorkspaceProfile 版本与迁移计划
  └── Billing / Ledger / Order

Gateway
  ├── OpenAI Responses / Chat 兼容入口
  ├── Anthropic Messages 兼容入口
  ├── 策略路由、健康探测与有限回退
  ├── 请求计量与幂等事件
  └── 上游适配器：签约线路、官方直连、共享算力、专属端点

Desktop
  ├── 目标软件发现与配置适配器
  ├── 系统安全存储中的 BYOK
  ├── 本地路由器、配置 diff、原子写入与回滚
  └── WorkspaceProfile 导入、迁移报告与 Secret 重新授权
```

关键边界：网页不直接写本机配置；Secret 不通过 URL 或 Profile 迁移；前端不自行计算生产余额、价格和线路健康；请求日志不等同于账本。

## 3. 供给聚合策略

不建议在所有中转站先大额储值。供给按四层经营：

| 层级 | 方式 | Moyusi 角色 | 资金策略 |
| --- | --- | --- | --- |
| 核心签约线路 | API 合作、代理或预付折扣 | 统一余额销售与 SLA 管理 | 小额滚动保证金，按实际消耗和信用额度扩张 |
| 官方模型渠道 | 官方 API 或云市场 | 直连或统一销售，取决于授权 | 优先月结/后付，避免过度预存 |
| 长尾中转站 | 用户自行选择 | 默认 BYOK，只做路由与健康信息 | 不代收、不囤余额 |
| 开放模型算力 | 共享 GPU、专属 GPU、自有端点 | 售卖推理用量或编排部署 | 共享池按量，专属资源先确认预算或预授权 |

统一充值只能覆盖有清晰转售权、成本可核验、可对账且可承担退款/故障责任的供给。其余来源应保持 BYOK 或外部结算，避免“中转站的中转站”变成不可控的资金池和责任链。

## 4. 开发主线

### 主线 A：模型与供给

先冻结 `Model → RouteOffer / ServingRevision → PriceVersion → EvidenceWindow`，再接供应商后台。广场只展示已发布且证据新鲜的供给。`EvidenceWindow` 必须绑定具体来源，至少记录 p50/p95、吞吐、成功率、样本数、地区和更新时间；模型级指标只能作为没有来源数据时的降级摘要。

### 主线 B：接入与权限

把统一余额、BYOK、共享算力、专属算力和自有端点分流成不同流程；形成 Entitlement、API Key、SecretBinding、EndpointConnection 和 DeploymentOrder。

架构先行批次已完成：前端现在通过 `PlatformModelGraph` 消费模型身份、版本、来源、RouteOffer、PriceVersion 与 ProbeWindow 的归一化关系；后续真实 API 只替换 repository adapter，不再让页面直接读取 fixture。

控制面读取投影也已建立：`ControlPlaneSnapshot` 统一连接项目、来源授权、脱敏 Key、Desktop、费用和 Workspace 资产，但不把这些对象合并成可写的大 JSON；后续命令接口仍按领域边界拆分。

控制面命令执行器已加入 mock 实现：命令先校验项目、来源、权限和 Desktop 前置条件，再返回可轮询的 `OperationResult`；本地操作在 Desktop 离线时会明确失败，不会产生半完成的路由或迁移状态。

### 主线 C：桌面路由

先支持 Codex 与 Claude Code 两个目标，完成发现、预览 diff、确认、写入、验证和回滚。路由失败只对已声明的超时、429 和可恢复 5xx 执行回退。

### 主线 D：调用与结算

Gateway 先支持语言/代码主链路。每次调用固定模型身份、实际线路和价格版本，生成幂等 UsageEvent，再结算到不可变账本。

### 主线 E：工作环境迁移

WorkspaceProfile 先覆盖 MCP、Skills 和 Prompts，再扩展经审核记忆与知识库。迁移必须给出 exact、adapted、rebuilt、unsupported 四类结果，不承诺厂商运行时无损复制。

## 5. 交付顺序与退出标准

### Stage 1：前端工程基线（当前）

- 正式 URL 与刷新/深链能力；
- 领域类型、接入策略和目录数据访问层；
- fixture 与组件之间建立仓库边界；
- 类型检查、单元测试和生产构建进入统一检查命令。

退出标准：模型详情与七个工作台子域可直接访问；五类供给进入正确业务边界；自动检查全部通过。

### Stage 2：Mock 端到端闭环

- Catalog、Offer、Workspace Summary 与 Key 的 mock API；
- 模型详情、供给选择、余额不足、BYOK 授权、自有端点验证状态；
- 创建演示平台 Key；
- Codex/Claude Code 的配置 diff、确认和回滚 fixture；
- “选模型 → 接入 → 保存路由 → mock 首次调用 → 用量可见”E2E。

退出标准：不依赖生产资金和真实 Secret，也能完整演示一次可恢复的接入。

当前进度：第一条“模型详情 → 统一余额/共享算力来源 → 保存路由 → 模拟调用 → 费用记录”闭环已完成。BYOK 已具备一次性本机授权入口和 Desktop 离线阻断；自有端点具备地址校验、脱敏端点引用和协议探测 operation；专属算力具备费用上限确认、DeploymentOrder 和创建中状态。迁移已具备“生成差异 → 用户确认 → mock 应用”的可记录流程。目录列表、模型详情和工作台摘要已通过 typed mock API 与通用异步资源状态读取；工作台已支持自动选择、固定来源、成本优先、优先地区与失败处理策略并持久化。真实桌面安全存储、配置写入和生产 API 仍待实现。

本轮补充：工作台摘要加入 DesktopConnection 状态。前端在 Desktop 离线或未安装时只展示策略和管理能力，不把本机配置写入或模拟调用误认为可执行；连接恢复后才显示本地路由可验证入口。

### Stage 3：Control Plane + Desktop Alpha

- 用户、设备、Catalog、Entitlement、API Key 摘要与 WorkspaceProfile；
- 桌面安全存储、本地代理和两个工具适配器；
- 设备授权、配置变更审计与回滚。

退出标准：测试账户能在本机安全接入一个 mock/沙盒来源，网页不接触明文 BYOK。

### Stage 4：Gateway + Metering Beta

- Responses、Chat Completions、Anthropic Messages；
- 签约上游与开放模型共享端点；
- 路由健康、幂等用量事件、价格版本与账本沙盒。

退出标准：每次调用和费用都能追到模型、线路、价格版本与结算事件，故障可回放。

### Stage 5：支付与受控公测

- 单一支付渠道、充值订单、退款和对账；
- 供应商准入、限额、熔断、告警和运营后台；
- 安全、隐私、许可证、性能与恢复演练。

退出标准：支付重放不重复入账，供应商或功能可独立关闭，账实差异可定位并人工处置。

## 6. 本轮已实现

- `/market`、`/market/:modelId` 与 `/workspace/:section` 正式路由；
- 模型详情、选中供给和目标工作台步骤可编码为 URL；
- 统一余额/共享算力进入路由，BYOK 进入本机授权，自有端点进入探测，专属算力在确认预算后创建部署订单；
- Catalog 类型、接入策略、数据仓库和 URL 生成器从页面中抽离；
- 模型详情已具备按来源的性能证据表、模型规格卡和能力矩阵，来源字段与模型字段分离；
- TypeScript 严格检查、Vitest 契约测试与 `pnpm check`；
- 11 个测试文件、50 个用例覆盖目录筛选、供给分流、命令边界、深链选择和本地演示状态。

## 7. 下一开发批次

控制面命令合同和五类供给前端分流完成后，下一批继续冻结可替换的系统边界：

1. 加入 `CatalogSnapshot / CatalogVersion` 发布状态，页面只消费可用且证据新鲜的来源；
2. 定义 `ApiRequest → RouteAttempt[] → UsageEvent → Settlement` 网关与计量合同；
3. 为 request、source event、price version 建立幂等键与失败分类；
4. 完善 Desktop Bridge 的配置 diff、确认、验证与回滚；
5. 加入关键路径 E2E，锁住“模型选择 → 命令执行 → 路由或部署生效 → 用量可见”。

在此闭环通过前，不开始真实充值、生产上游凭证或本机配置写入。

## 8. CC Switch 截图核对后的主线调整

CC Switch 是 Moyusi 当前的主要竞品和能力参照对象。后续评审不以“页面看起来更简单”为完成标准，而以“关键能力是否完整、用户是否更容易完成任务”为标准：CC Switch 已验证的本机切换、Provider、项目、工具发现、认证、备份、会话、MCP、Skills、Prompts、统计和诊断能力，不能因为 Moyusi 采用极简视觉就被无意删掉。

逐页核对 CC Switch 后，下一批不再按“设置页”堆叠功能，而按四个可验证闭环推进：

1. **Provider 与来源**：预设来源、BYOK、统一 Provider Profile、自定义协议探测；
2. **路由与本机执行**：RouteProfile、同模型回退、健康检查、Desktop 心跳、配置 diff、备份和回滚；
3. **工作环境与会话**：MCP/Skills/Prompts 统一资产列表、目标应用适配、Session Index 和迁移报告；
4. **用量与诊断**：请求事件、实际线路、价格版本、账本、外部 BYOK 估算和连通性诊断。

工作台导航收敛为五组：开始（总览/模型切换）、接入（来源与凭证/模型与部署/工具与设备）、工作环境（配置与迁移/会话）、费用（用量与请求/余额与账单）、设置（偏好/数据/安全）。`account` 保留兼容路径，但不再作为顶层产品入口。

详细截图证据、页面能力矩阵、P0/P1/P2 取舍和分阶段退出标准见 [15-cc-switch-capability-matrix.md](./15-cc-switch-capability-matrix.md)。

### 能力对齐规则

- **保留能力，重做表达**：CC Switch 已证明有价值的能力继续保留，前端改成任务导向、渐进披露和可读状态。
- **不复制实现**：Moyusi 可以复用公开许可允许的思路或兼容协议，但不复制 CC Switch 品牌、界面资产或未经确认的实现代码。
- **先 Web 统一，再 Desktop 落地**：模型、来源、策略、资产和费用在 Moyusi Web 统一管理；本机文件、进程、系统密钥、代理和升级由 Desktop 执行。
- **每项能力必须可验证**：新增能力必须有成功、失败、离线、回滚或不支持状态，不能只做静态按钮。
- **竞争差异放在上层价值**：Moyusi 不与 CC Switch 比谁的 Provider 名单更长，而是提供同型号来源比较、统一充值、开放模型算力和跨工具工作环境迁移。
